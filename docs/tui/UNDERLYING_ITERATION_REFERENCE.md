# TUI / 运行时底层迭代参考

> **用途：** 为后续自用迭代提供方向地图与取舍备忘，不参与对外版本叙事。  
> **维护假定：** 本仓库中的 TUI 与共享 runtime 已与上游产生较大分歧，**不宜假设能无痛跟随外部升级**；演进以本仓库内增量迭代为主。

## 1. 文档怎么用

- 将下列各节视为 **可选增量（increments）**，按团队优先级拆 issue / 里程碑，而非一次性项目。
- 实施前在对应代码区（`crates/tui/src/core/`、`session_manager`、compaction、tools 等）做一次现状核对；本文件不追踪行级实现细节。
- 与 CRAFT 草案重叠处（黑板、角色工具边界、Verifier 结构化输出）以 **可靠性** 为主线；其余以 **性能、可维护性、可观测性** 为主线。
- 若当前目标是「尽快完善底层再上独有功能」，优先阅读 **[§2.1](#21-快车道先打底再独有功能)** 与 **[运行时演进路线图](../tech/RUNTIME_EVOLUTION_ROADMAP.md)** §1.6（**独有功能 / 桌面 GAP 高峰在 P2 后**），再对照 [§4](#4-与阶段-ab-的对应关系) 映射到各技术小节。

## 2. 维护背景（为何「自迭代」）

- TUI 与引擎职责仍集中在 `crates/tui`（及逐步拆出的 workspace 子 crate），与官方或第三方一条龙的「升级即合并」路径解耦。
- 大改动后，合并外部大版本往往成本高于内部分模块重构；**方向选择应优先服务本仓库产品（含 DS Pick 共用 runtime）**，而不是假设与某条公开分支对齐。

### 2.1 快车道：先打底，再独有功能

Agent 产品与模型能力迭代很快；**底层缺口会在独有功能上放大成返工**（会话崩、事件不兼容、工具边界不清）。建议用一条明确的 **「打底完成线」** 限定底层投入，避免无限期「再稳一点」。

| 阶段 | 目的 | 说明 |
|------|------|------|
| **A. 打底（平台最小可行）** | 长跑与集成不拖后腿 | 聚焦：会话/容量、可观测、失败路径、一条关键回归。达到完成线即允许并行做 B。 |
| **B. 独有功能（产品差异化）** | 与赛道拉开差异 | 在共享 runtime 上叠：工作流、黑板/任务态、桌面体验、行业或团队工作方式等；参考 [CRAFT 草案](../agent-reliability-craft-plan.md)。 |

**打底完成线（建议当作里程碑验收，可按实际收紧/放宽）：**

1. **会话与容量：** 对「典型长跑」有内部标准（例如连续多轮 + 大工具结果场景）下，内存与主线程阻塞**可接受或有明确上限**；compaction/trim 与 UI/落盘**无已知静默分叉**类 bug。  
2. **可观测：** turn 级至少具备一种**结构化**输出（日志字段或 `Event` 扩展），能回答：第几步、用了哪些工具、因何结束。  
3. **失败路径：** 网络错误与可分类的 API 业务错误（如 400）走**不同**用户可见提示；高风险路径有单测或脚本门禁更好。  
4. **跨表面契约（若已用桌面/HTTP）：** 对外部消费的事件或 API 有**文档化子集**或版本字段，避免独有功能开发时反复协议撕扯。

达到 **1 + 2** 即可开始写独有功能原型；**3 + 4** 与独有功能并行补齐也可，但不宜长期缺位。

### 2.2 已定序的差异化里程碑（当前）

下列顺序为本仓库 **阶段 B** 当前的执行次序：先做 **可追溯多智能体与闭环（CRAFT）**，再系统化 **话题记忆地图**。

| 顺位 | 方向 | 说明 |
|------|------|------|
| **①** | **继续完善 CRAFT** | 黑板 / 角色级工具裁剪 / Review→修复闭环 / Verifier 结构化产物等；实施清单见 [Agent 可靠性 CRAFT 草案](../agent-reliability-craft-plan.md)。 |
| **②** | **记忆地图（Topic Memory Graph）** | 从对话文本维护 **topic 图**（简单衰减、关联、可选情绪/轨迹启发信号），并可生成适于注入 agent 上下文的 Markdown 片段；源自独立库 [**topic-memory-graph**](https://github.com/didclawapp-ai/topic-memory-graph)（TypeScript，`pnpm add topic-memory-graph`，**零运行时依赖**，MIT）。宿主侧可自行将 `graph` 存为 JSON（文件、Tauri、IndexedDB 等）。 |

**CRAFT 与记忆地图的分工（避免重叠扯皮）：**

- **CRAFT 黑板：** 偏向 **单次任务内的结构化交接**（findings、`observed`/hypothesis、blockers、`verdict` 等），与 `agent_spawn` 角色链绑定。  
- **记忆地图：** 偏向 **跨轮次的话题结构与热点延续**（何主题被反复触及、关联边、衰减），为「长期会话仍知道在聊什么大块」服务，不等于任务验收状态机。

**并入本单体时的集成注意：** 运行时以 Rust（TUI + sidecar）为主，记忆地图库为 TS —— 可选路径包括：**桌面 Web UI 或服务端侧维护图并重放为注入块**；TUI-only 路径则需 **Rust 侧对等实现或小进程边界**（IPC/子进程汇总），避免在无 Node 的环境里硬绑 JS。无论哪条路径，写入 **prompt / AGENTS.md 式注入**时都要约定 **优先级、裁剪与隐私**（不注入密钥、不过度冲淡当前 turn 的工具结果）。

### 2.3 记忆地图：现状与可挖掘潜力

当前实现（含 [**topic-memory-graph**](https://github.com/didclawapp-ai/topic-memory-graph)）仍偏 **雏形**：从对话增量维护图、简单衰减与关联、导出一段可注入上下文的 Markdown。价值已能验证「跨多轮仍可 grasp 话题脉络」，但**不必停在 prompt 贴片层**——下列方向可作为中后期差异化储备（任选其一切片立项即可）：

| 方向 | 思路提要 |
|------|----------|
| **接地（grounding）** | 节点/边附上 **仓库路径、提交、CRAFT 黑板 `task_id` 或条目 id**，使「热点话题」可一键跳到证据，而不只是 NLP 摘要。 |
| **多租户与多尺度** | **工作区 / 仓库 / 用户** 多层级图：哪些结构全局稳定、哪些仅本会话衰减快；合并策略与隐私边界写清楚。 |
| **与 compaction 共生** | 上下文被摘要或裁剪后，**图作为丢失细节后的拓扑备份**——Compaction 缩写历史，图为「还剩哪些大块在拉扯注意力」。 |
| **检索式注入** | 非每轮粘贴整段 `generateMemorySection`；按 **当前 turn 关键词 / working set 路径** 取 **k-hop 子图** 再生成短块，兼顾 token 与相关性。 |
| **产品化 UI 与运维** | 力导向拓扑、热点列表、时间轴（可参考该库 README 里的实验 UI 思路）；支持 **导出/对比/回滚** 图版本，便于调试与信任。 |
| **工具与地面真值** | 在允许的前提下，从 **只读工具结果**（如 `grep`、`read_file` 摘要）抽取实体写入图，弱化纯聊天臆测话题边；须与密钥与冗余存储策略对齐。 |
| **评测闭环** | 定义轻量指标：重复澄清同一主题的轮次是否下降、inject 是否改善长会话任务完成率——避免「体感很强、数据没有」。 |

以上为 **路线图备忘**；落地仍建议 **CRAFT（§2.2①）** 先架起任务态与注入纪律，再上 **规模化记忆地图**，以免多源上下文无仲裁规则。

### 3.1 引擎与编排 (`core/engine`)

**现状意图：** turn loop 负责取消 token、steer 插队、刷新 system prompt、max steps、自动 compaction 等。

**可参考增量：**

- **结构化可观测性：** 单次 turn 内步骤 index、选用的工具、提前结束原因（用户取消 / max steps / 错误）——以结构化事件或日志输出，减少对纯文案 `status` 的依赖，便于 headless / 桌面侧消费。
- **背压与优先级：** steer、流式 delta、工具进度并发时，明确 channel 侧合并或丢弃策略，避免 UI 饥饿或抖动。
- **失败恢复：** 对可预期 API 错误（如 thinking 模式下 `reasoning_content` 约束导致的 400）建立少数稳定恢复路径（重试、上下文修补、用户可见说明），避免分散的特判蔓延。

---

### 3.2 会话与持久化

**动机：** 长跑会话中 `api_messages` / 历史与会话保存易线性增长，内存与 serde/落盘成本突出；与 AGENTS 中「无默认自动裁剪」的策略共同构成运维风险。

**可参考增量：**

- **分层存储：** 热窗口（近期消息 + pin）、冷区（摘要 / compaction 产物）、大体量工具结果用引用或外部化存储，按需再注入。
- **落盘健壮性：** 节流写入、crash-safe 或 checkpoint，避免超长序列化阻塞主循环。
- **一致性：** compaction 或 trim 改写 `session.messages` 时，与 TUI transcript、revision、会话文件的语义对齐，防止静默分叉。

---

### 3.3 容量与 compaction

**现状意图：** capacity flow 与 turn 内 `should_compact` / `compact_messages_safe` 等路径配合，失败时可回落到本地裁剪。

**可参考增量：**

- **估算校准：** token/成本估算与 provider `usage` 对照或分块统计，提高阈值触发的可信度。
- **触发维度：** 除比例阈值外，对「工具结果骤增」「单条超大 diff」等设置紧急策略。
- **压缩验证：** 压缩后校验必选 pin、关键契约字段；失败则拒绝提交新历史并告警，避免静默丢上下文。

---

### 3.4 工具运行时与信任边界

**与 CRAFT 草案对齐：** 角色级权限、共享黑板、Verifier 结构化输出、Review→修复闭环。

**可参考增量：**

- **按角色工具白名单：** 在 runtime 注册或派发前裁剪工具集，强化只读类角色（如 explore/review）无写路径；`custom` 等角色保持显式白名单。
- **黑板 / 任务态：** Explorer findings、Verifier 的 observed/hypothesis 分层、Reviewer blockers 等结构化写入，并在 `agent_spawn` 时注入子会话，减少主 agent 自然语言转述损失（详见 `docs/agent-reliability-craft-plan.md` 中的 schema 草案）。
- **闭环协议：** Verifier 失败 → 结构化交付 Implementer → 固定模板或程序化触发再一轮，而非单次评论即结束。

---

### 3.5 事件与 UI 边界

**现状意图：** `core/events.rs` 经 channel 驱动 ratatui 与 one-shot 等模式。

**可参考增量：**

- **事件契约：** 对桌面 Web UI、HTTP/SSE、CLI 非交互模式暴露的稳定事件子集与版本字段，减少枚举变更的连锁破坏。
- **大负载：** 工具进度或超大输出改用句柄（id、路径）或分块引用，降低 clone 与队列压力。

---

### 3.6 模块边界与入口

**现状意图：** `crates/tui` 仍为现场运行时；workspace 内向 `crates/core` 等拆分在进行中。

**可参考增量：**

- **瘦身 `main`：** CLI 解析、TUI 主循环、one-shot 路径分层，降低合并冲突与单测门槛。
- **单一事实源：** session/turn/capacity 逻辑避免在 TUI 与 `crates/core` 双份漂移；重构时优先收敛到共享 crate 再删重复。

---

### 3.7 LLM 客户端与协议边缘

**可参考增量：**

- **流式解析：** thinking 块、tool call 交错、截断响应的恢复与超时行为明确化。
- **配置与错误对齐：** beta/strict tool 等开关与服务端 400 文案映射到可操作提示。
- **重试策略：** 区分网络可重试与业务不可重试，避免无效重试与额度消耗。

---

### 3.8 可测试性与回放

**可参考增量：**

- 将 compaction pin、working set、容量快照等抽成易测纯函数，辅以属性测试（例如 pin 后关键消息不被删除）。
- 最小事件序列录制/回放，回归 turn loop 与工具编排。

## 5. 建议的优先级备忘（可随时重排）

以下为 **启发式排序**，实施时应用数据与痛点验证：

1. **会话与消息存储瘦身**（内存 + 落盘 + 与 compaction 一致）——对稳定性与长跑体验影响面最大。  
2. **角色工具策略 + 黑板 MVP**——与现有 subagent 叠加，提升多智能体可靠性。  
3. **引擎可观测与失败恢复**——缩短线上/集成问题定位时间。  
其余条目按产品与性能瓶颈插入。

---

## 6. 非目标（本参考不承诺）

- 替代人工对需求与风险的最终确认。  
- 保证模型输出字面意义「确定性」；工程上强调的是 **门禁、可重复验收与可追溯状态**。  
- 与未经验证的外部大版本「一键合并」对齐。
