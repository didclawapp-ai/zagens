## 0. TL;DR

| 问题 | 立场 |
|------|------|
| 全新项目生成主模型串行太慢，能否并行？ | **能** —— 子代理基础设施已是真并行（独立 tokio 任务 + 各自 LLM 流），缺的是「契约优先 fan-out/join」这条编排链路 |
| 重构 / 修复能否同样并行？ | **不能**（§1.2）。已存在代码互相耦合，并行 agent 互相抽地毯，冲突是语义级、文件锁拦不住 |
| 直接把 N 个文件丢给 N 个子代理？ | **不行**。接口不一致 → 集成期全崩。必须**契约优先**：先冻结模块划分 / 公共接口 / 共享类型 / 错误类型 / 依赖清单 |
| 契约写完就分发？ | **不行**。契约错误的代价在并行下 **N× 放大**。分发前必须 **P0.5 固化闸门**（程序化 + 2–3 轮审 → 收敛冻结 / 不收敛降级回串行） |
| 子代理全做完就集成？ | **不行**。集成前必须 **P1.5 符合性审核闸门**（逐模块对冻结契约审 → pass 才放行）。契约没实现对，进集成没意义 |
| **这方向是不是臆想的？** | **设计不是**（地基代码已核实、套用成熟实践）；**但「值不值得做」是未验证假设** —— 串行慢的痛点没量化、串行开销可能吃掉并行收益（Amdahl）、单模型并发限流未测。**先证伪前提再谈落地**（§7.1） |

**一句话流水线:**
`P0 出契约 → P0.5 固化闸门 → 冻结(hash 锁) → P1 并行实现 → P1.5 符合性闸门 → P2 集成构建 join`

**两道闸门 = 经典 V&V 分工:**
- **P0.5 = build the _right_ thing**（契约本身对不对，分发前）
- **P1.5 = build the thing _right_?**（实现忠不忠于契约，集成前）

## 1. 背景与动机

### 1.1 现象

全新项目/模块生成目前由主模型**串行**完成：一个文件接一个文件写。对一个 N 模块的新项目，墙钟时间 ≈ N 个模块串行之和。模块之间在「实现细节」上本可互不依赖，串行是纯粹的时间浪费。

### 1.2 为什么全新生成能并行、重构/修复不能（本方案的根因）

本质区别是**依赖方向与契约稳定性**：

- **重构 / 修复**：工作对象是*已存在且互相耦合*的代码。改 A 的函数签名会波及 B/C 的调用点；任何并行 agent 都在对方脚下抽地毯 —— 冲突是**语义级**的，文件级互斥锁拦不住。**结论：不并行。**
- **全新生成**：起点为空，且**契约可以先冻结**。一旦把「模块划分 + 公共接口 + 共享类型 + 错误类型 + 依赖清单」定死，各模块的实现就**只依赖那份冻结契约、互不依赖对方内部** —— 这才是可并行的根因。

> 推论：可并行性 = 「模块实现细节之间的依赖能否被一份冻结契约完全屏蔽」。屏蔽得了就能并行，屏蔽不了（如重构）就不能。**P0.5 的核心职责就是验证这条屏蔽成立**（依赖独立性）。

### 1.3 并行的代价结构（为什么要两道闸门）

并行的代价是**不对称**的：

- 串行模式下，契约里的一个错误只坑主代理自己，改一处即可。
- 并行模式下，契约错误会让 N 个 implementer **全部基于错误假设写完**，发现时要 **N× 回滚 + 重新分发**。

所以正确的工程动作是：**把审查成本前置到串行、便宜的阶段去花**（P0.5 固化、P1.5 逐模块卡），而不是让它在并行、昂贵的阶段爆炸。这与人类工程方法论一致：最省钱的审查是「动手前审方案」+「集成前验收件」。

> **⚠️ 但这把双刃剑也指向本方案自己（Amdahl 定律）：** 加速比受**串行占比**封顶。本流水线里 P0（出契约）、P0.5（2–3 轮串行审）、P2（集成 + 全局 build/test）**全是串行段**，只有 P1 并行。设串行占总工作量比例 \(s\)、并行度 \(N\)，则加速比 \(\le 1/(s + (1-s)/N)\)。若 P0+P0.5+P2 占了一半工作量（\(s=0.5\)），即便 \(N=\infty\) 也最多 **2× 提速**；模块越少、契约越重，\(s\) 越大、收益越薄。**这正是 §7.1 必须先量化的核心风险**：串行开销很可能在中小项目上吃掉甚至反超并行收益。

## 2. 现有基础设施盘点（复用 vs 新建）

并行能力**地基已具备**，详见 `crates/runtime-server/src/tools/subagent/`：

| 能力 | 现状 | 文件锚点 |
|------|------|----------|
| 真并行执行 | 每个子代理是独立 tokio 任务（`JoinHandle`），各跑自己的 turn loop、各开一条 LLM 流 | `subagent/runtime.rs`（`SubAgent.task_handle`） |
| fan-out / join | `agent_spawn` 多个 + `agent_wait(mode=all)` + `agent_result` | `subagent/tools/{spawn,wait,result}.rs` |
| **并行写不撞车** | **文件租约**：一个 agent 独占一个文件路径，冲突直接拒绝 spawn（硬锁） | `subagent/resident.rs`（`try_claim_resident_file_lease`） |
| 协调 / 进度 | 黑板（共享）+ mailbox（结构化进度） | `subagent/blackboard.rs`、`subagent/mailbox.rs` |
| 安全护栏 | 深度上限、取消级联、per-step 超时、僵尸扫描 | `subagent/runtime.rs`（`max_spawn_depth`/`cancel_token`）、`constants.rs` |
| 实现型角色 | 子代理类型已含 `implementer`/`builder`/`worker` | `subagent/constants.rs`（`VALID_SUBAGENT_TYPES`） |

**关键约束（影响隔离粒度）：** 所有子代理**共享同一个 workspace**（`child_runtime` 仅 clone context，workspace 路径不变），**没有 per-agent 的 git worktree 隔离**。所以并行隔离粒度是「文件级互斥锁」，不是「各写各分支再合并」。本方案据此设计 —— 用租约保证文件独占，用契约保证跨文件一致。

**需要新建：** 一个 **LHT 感知的「契约优先 fan-out 规划器」**，把现有任务图（plan/checklist）切成「互相独立的文件组 + 一份冻结契约」，外加两道闸门（P0.5 / P1.5）与集成 join。天然挂在 [LHT harness](./LONG_HORIZON_CODE_TASKS.md) 上。

## 3. 流水线总览

```
P0   主代理出契约（含每模块「符合性测试」）
      └─ 目录布局 / 依赖清单 / 模块 wiring / 公共 trait·接口 / 共享类型 / 错误枚举（实现体 todo!()）

P0.5 契约固化闸门  ← build the RIGHT thing
      ├─ 程序化（硬）：骨架可编译 / 依赖图无环且=租约边界 / 每 checklist 项↔唯一 owner
      ├─ 认知（软，2–3 轮 review-modify）：完整性 / 一致性 / 独立性
      └─ 收敛准则：闸门全绿 + 本轮无接口级改动 → 冻结；2–3 轮不收敛 → 降级回串行（可行性判定器）

──   冻结：contract.lock + hash；P1 期间骨架/契约文件写被租约拒绝

P1   并行 implementer（fan-out，并行度 3–5）
      └─ 各 pin contract hash、各占 resident 租约、对契约做 TDD、禁止改骨架/共享文件

P1.5 契约符合性审核闸门（join 后、集成前）  ← build the thing RIGHT?
      ├─ 程序化（硬）：接口指纹比对 / 对冻结契约编译 / 跑契约自带测试 / 无 todo!() 残留 / 租约外零改动
      ├─ 认知（软）：语义符合补审
      └─ 失败：scoped fix agent 只修该模块（有界轮数）→ 反复失败 → 回退契约修订

P2   集成 + 全局 build/test join
      └─ 主代理/integrator wiring → build/test → 失败派 fix agent
```

## 4. 各阶段详述

### 4.1 P0 — 契约起草（串行，主模型）

主模型先产出**可编译的骨架**，而非直接写实现：

- 目录布局；依赖清单（`Cargo.toml` / `package.json`）；模块 wiring（`mod.rs` / `lib.rs` / `index`）；
- 公共 trait / 接口 / 数据类型 / 错误枚举；实现体先 `todo!()` / `unimplemented!()` 占位；
- **每模块的符合性测试**（见 §4.5 为何这是 P0 的产物而非 P1.5 现编）。

这一步**必须串行** —— 它定义了后续所有并行的边界。产物是一份「契约工件」。

### 4.2 P0.5 — 契约固化闸门（串行，分发前）⭐ 设计评审前置金矿落点

单模型「再审一遍契约」易成回声室。按抗幻觉哲学（**S3 程序化校验 > S1 双模型 Judge**，见 [`../agent-reliability-craft-plan.md` §11.5](../agent-reliability-craft-plan.md) 配套结论），审查**先程序化、后认知**：

**① 程序化闸门（硬，过不了打回）：**
- **骨架必须能编译**（`todo!()` 占位）：编过 = 类型/签名/可见性/依赖在编译器层面自洽。**这是最强的一道契约校验。**
- **依赖图无环 + 模块边界 = 租约边界**：证明分解是真「独立」的，而非表面分了实则互调内部。**这是并行正确性的前置条件**，比任何文字审查都重要（呼应 §1.2 屏蔽推论）。
- **每个 checklist 项恰好映射到一个文件组 owner**：证明没有两个 agent 会写同一文件（与 resident 租约对齐）。

**② 认知审查（软，2–3 轮 review-modify，带清单）：**
- **完整性**：每个模块的输入/输出/错误路径是否都在契约里有落点？有无「实现时才会冒出来的共享类型」？
- **一致性**：跨模块命名 / 错误类型 / 序列化格式是否统一？
- **独立性（最该盯）**：把每个模块想象成黑盒，它能否只靠契约 + 自己内部完成？若某模块「需要知道另一模块怎么实现的」，说明契约漏了抽象，**必须补进契约或合并模块**，否则不能并行。

**③ 收敛准则（别无限审，防新死循环）：**
- 程序化全绿 **且** 本轮认知审查无接口级改动（只剩措辞）→ **冻结**。
- 硬上限 2–3 轮：仍不收敛 → 任务分解本身有问题 → **降级回串行**（主模型自己写）。
- 故 P0.5 同时是个**可行性判定器**：不是所有「全新项目」都适合并行。

### 4.3 冻结语义

冻结 = 产出一份**带 hash 的契约工件**（如 `.deepseek/contract.lock`，或并入现有 [handoff 机制](./LONG_HORIZON_CODE_TASKS.md)）。每个 implementer 启动时 **pin 这个 hash**；P1 期间**任何对骨架/契约文件的写都被租约拒绝**。这样「契约不可变」是**机制保证**，不靠提示词约束。

### 4.4 P1 — 并行实现（fan-out）

- 每个 implementer 认领一组文件（`resident` 租约独占）、只读冻结契约、只写自己那组、**禁止改骨架/共享文件**。
- 对契约做 **TDD**（契约自带测试已在 P0 冻结，implementer 的目标就是让它们变绿）。
- **并行度建议限 3–5**：并行省的是墙钟时间，花的是 token 与 DeepSeek 并发流配额（见 §7 风险）。

### 4.5 P1.5 — 契约符合性审核闸门（join 后、集成前）⭐

> **为什么必须集成前、逐模块、对契约审？** 若先集成再统一 build，模块 A 的契约违例会以「依赖 A 的 B 编译/测试报错」的形式冒出来，你会在 B 里 debug、根因却在 A。**对着冻结契约逐模块隔离审，把故障锁死在违例模块**，不让它顺依赖链污染下游。一个接口漂移的模块会毒死所有依赖它的人，必须在它进集成池**之前**就拦在边界上。

**破解单模型回声室的关键 —— 可审性前移：**

> 契约（P0/P0.5）**必须连同「每模块符合性测试」一起冻结**。这样 P1.5 主体退化成「对每个模块跑契约自带测试」，是程序化的，不是 vibes。这也是为何符合性测试是 §4.1 P0 的产物。

**① 程序化（硬，过不了打回该模块）：**
- **公共接口指纹比对**：抽出 implementer 产物的公共 API 表面（签名/类型/错误变体），与 `contract.lock` 冻结表面 diff，**任何漂移 = 拒绝**（机械可算：填血肉可以，动骨架契约不行）。
- **对冻结契约编译**（而非对兄弟模块真实现）：证明它没偷改接口迁就自己。
- **跑契约自带符合性测试** + **无 `todo!()`/`unimplemented!()` 残留**（复用 LHT `[verify:]`「做完 ≠ 跑通」原则，粒度落到模块）。
- **租约外文件零改动**（hash 校验骨架/契约文件没被动过）。

**② 认知审查（软，只补程序化抓不到的）：**
- 主抓**语义符合**：签名对、测试也过，但行为与契约意图不符（契约测试覆盖不全时）。放在程序化全绿之后，作补漏，不作主判据。

**③ 失败处理（决定方案省不省钱）：**
- 单模块不符合 → **只对该模块**派 scoped fix agent 重做 + 重审，有界轮数；**其他已通过模块不受影响**（逐模块审的红利）。
- 某模块**反复**不符合 → 信号变了：**很可能契约本身错了** → 回退到契约修订。契约一改可能让其他已通过模块作废 —— **这是最贵的情况**，也正是 P0.5 存在的全部意义（把这种灾难尽量挡在分发前）。

### 4.6 P2 — 集成 + 全局构建 join（串行）

主代理 / integrator 收口 wiring → 全局 `build` / `test` → 失败派 fix agent。编译和测试是天然的全局串行关卡。

## 6. 关键设计原则

1. **程序化优先**：两道闸门都「先程序化（编译/依赖图/接口 diff/契约测试）、后认知」。让不会幻觉的工具当终审（S3 > S1）。
2. **降级出口**：P0.5 不收敛 → 回串行；并行是**可选优化**，不是默认。可行性由闸门判定，不是无脑铺开。
3. **回退链画明**：P1.5 反复失败 → 回契约修订（最贵路径），设计须显式承认并 bound 它。
4. **成本/限流上限**：并行度有硬上限；N× token 与并发流配额要算账（见 §7）。
5. **机制 > 提示词**：契约不可变靠租约 + hash pin，不靠「请不要修改」的提示词。

### 6.1 理论锚点（这不是凭空设计，每条都对应成熟工程理论）

本方案没有发明新范式，是把以下成熟理论/实践**套用**到 agent 编排上 —— 这是「方向是否扎实」的依据，但也仅限于「方法成熟」，**不等于「在本场景值得做」**（后者见 §7.1）：

| 本方案要素 | 对应的成熟理论 / 实践 | 套用关系 |
|------|------|------|
| 「全新可并行 / 重构不可」 | **依赖分析 / embarrassingly parallel**：无数据依赖的子任务才可并行 | 契约屏蔽了模块间的实现依赖 → 把「不可并行」转成「可并行」 |
| 契约优先、先冻结接口再实现 | **API-first / 接口先行**（protobuf、OpenAPI、设计契约 Design by Contract，Meyer） | 团队协作里先定接口再各自实现的标准做法，搬到子代理上 |
| 两道闸门（P0.5 / P1.5） | **V&V 分工**：Validation（做对的东西）/ Verification（把东西做对） | P0.5=V，P1.5=V，分别卡分发前与集成前 |
| 串行开销封顶收益 | **Amdahl 定律** | §1.3 已量化：串行占比 \(s\) 决定上限，是本方案最大风险的理论来源 |
| 程序化优先于模型审 | **形式化/可执行验证 > 人审**（编译器、类型系统、测试是判定式 oracle） | 与仓库既有结论 S3>S1 一致（[`craft-v2-improvements.md` §4](../craft-v2-improvements.md)） |

> **诚实边界：** 上表证明「方法有出处」，**不证明「收益为正」**。Amdahl 同样是成熟理论，而它恰恰预测本方案在中小项目上可能不划算。理论支撑是双向的 —— 它既给方案背书，也给「先别做」背书。

## 7. 风险与未决问题

| 风险 / 问题 | 说明 | 缓解 |
|------|------|------|
| **契约质量决定一切** | P0 没定死的接口，P1 必然各猜各的 → 集成爆炸 | P0.5 闸门 + 契约自带测试 |
| **成本翻倍** | N 并行 agent = N× token | 并行度上限 3–5；仅对「模块数多、彼此独立」的项目启用 |
| **并发流限流** | DeepSeek 并发 SSE 流可能撞速率限制 | 并行度上限；失败回退串行 |
| **与单模型路线张力** | Zagens 卖点是「单模型深度适配」，铺开很多浅上下文 agent 与此略拧 | 定位为**可选加速**，非主线；先量收益再推 |
| **语义符合难机检** | 签名对但行为错，纯 API diff 抓不到 | 契约自带行为测试（前移）；P1.5 认知补审兜底 |
| **共享文件归属** | 清单/模块导出/lib 入口谁拥有 | 骨架/共享文件归 P0/集成者，implementer 不碰（租约拒绝） |
| **无 worktree 隔离** | 子代理共享 workspace，靠文件锁而非分支 | 文件级租约 + 契约跨文件一致；worktree 隔离列为后续可选增强 |

### 7.1 该不该做：待验证前提（⚠️ 落地前必读，防止把假设当结论）

本方案的**设计**是自洽的（§6.1），但它建立在几条**尚未用数据验证**的前提上。把它们摊开，避免「逻辑自洽」被误读成「值得做」：

| # | 未验证前提 | 不成立则方案失效的方式 |
|---|------|------|
| A | **「串行慢」是当前真痛点** | 若真实痛点是正确性（截断/早停/假绿，仍在收口中）而非速度，则这是**优先级错配**——性能优化压在尚未完全可靠的系统上 |
| B | **并行收益 > 串行开销**（Amdahl，§1.3） | 中小项目串行段（P0+P0.5+P2）占比高 → 实测可能**比纯串行还慢**，只剩 N× 成本 |
| C | **单模型/单 key 下并发流不被限流** | DeepSeek 并发 SSE 撞速率限制 → 墙钟收益当场蒸发 |
| D | **模型能一次产出可冻结的完整契约** | 长程任务失败根因正是模型长跨度不可靠；若契约老写不对，P0.5 反复打回 → 只在简单项目生效（而简单项目不需要并行） |

**去风险实验（先证据、后代码；做完前不写规划外任何代码）：**
1. **量痛点（验 A/B）**：拿一个真实大型全新项目（如 2W 行解释器），测纯串行的墙钟 + 成本，确认「慢」到底有多痛、痛在墙钟还是成本。
2. **手动模拟一次 fan-out（验 B/C/D）**：人工把它切 3–4 个独立模块、手动开几个子代理跑，观测：(a) 契约能否一次冻结、(b) 并发流是否被限速、(c) 集成期返工量。**一次手动实验即可证伪或证实大半**，成本远低于建整套机制。
3. 两组数据出来前，本方案维持 **⬜ 规划中**，不进开发。

> **结论：** 这是一份**诚实的「待验证方向」**，不是已拍板路线。理论给了它背书，也给了「现在先别做」背书（Amdahl）。把它当成「等到有大型项目实测证据时再激活」的 backlog，而非下一步要写的代码。

## 8. 落地路线（先文档，0.8 之后）

与 §11.5 同步：**0.8 引擎分离之后再做**（先把幻觉率与稳定性踩平，勿同时调多个动目标）。建议分期：

1. **本文档**（设计 SSOT）✅ 当前。
2. **🚧 去风险实验闸门（§7.1，硬前置）**：先跑「量痛点 + 手动模拟一次 fan-out」两组实验。**结论为负（串行够用 / 并行被限流 / 契约冻不住）则就此打住，不进下面任何一步。** 这是阻止「臆想落地」的关卡。
3. **契约工件 schema**：`contract.lock` 字段（模块表、接口指纹、文件组↔owner 映射、符合性测试索引、hash）。
4. **P0.5 程序化闸门原型**：骨架编译 + 依赖图无环且=租约边界 + 项↔owner 唯一性 三项自动校验。
5. **fan-out 规划器**：任务图 → 文件组 + 契约；并行闸门（仅当模块声明独立且契约冻结才 fan-out）。
6. **P1.5 闸门**：接口指纹 diff + 对契约编译 + 跑契约测试 + 失败 scoped-fix/回退。
7. **集成 join + 端到端串起**；遥测（并行收益 vs 成本）先量后调。

> 第 2 步是硬闸门：**3–7 全部 gated 在它通过之后**。
