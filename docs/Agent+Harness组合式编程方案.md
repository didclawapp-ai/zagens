## 一、问题定义

### 1.1 当前 Agent 编程的核心瓶颈

| 瓶颈 | 表现 | 根因 |
|------|------|------|
| **推理衰减** | Agent 写到一半就"觉得做完了"，实际目标未达成 | LLM 的注意力随生成长度指数衰减，原始目标从注意力窗口消失 |
| **目标漂移** | 写着写着偏离原始需求，写了一堆辅助函数忘了核心流程 | 没有持久化的任务结构来锚定目标 |
| **自主权困惑** | 每个小决策都问人（效率低），或者重要决策不问人（风险高） | 缺少"决策重要性分级"机制 |
| **沉默失败** | Agent 陷入循环/错误方向，不断重复却不自知 | 缺少行为模式的外部监控 |
| **黑盒焦虑** | 人看不到 Agent 在干什么、为什么这么做、做到哪了 | 内部状态未外化 |
| **上下文天花板** | 长任务超出上下文窗口，压缩导致关键细节丢失 | 上下文压缩用"概括"替代"记忆"，不可概括的信息被丢弃 |

### 1.2 核心洞察

**Agent 编程当前最大的阻碍不是模型能力不够，而是结构不对。** 模型是被动响应式的——`f(prompt) → response`。它没有任务概念，没有持久记忆，没有自我监控。解决这些问题的正确位置不是模型层，而是 **架构层**——在模型之上构建一套 Harness 系统。

### 2.2 核心关系三角

```
            Harness（系统信任）
             规则/验证/边界
            /              \
           /                \
          /                  \
    黑板（数据层）      可视化（呈现层）
   结构化状态             人可理解的界面
   交接工具              解决黑盒焦虑
```

- **Harness** 产生事实——验证结果、干预触发、约束状态
- **黑板** 存储事实——结构化、可交接、可追溯
- **可视化** 呈现事实——让人看见、理解、信任

三者缺一不可：Harness 保证系统可靠，可视化让人感受到这种可靠。没有可视化的 Harness 是一个黑盒里的保险箱。

## 三、Prompt 演进与 Harness 体系

### 3.1 四阶段演进

```
阶段一：简单 Prompt          阶段二：带约束 Prompt
┌──────────────────┐       ┌──────────────────────────┐
│ 人说 WHAT         │  →   │ 人说 WHAT + HOW           │
│ 模型全权决定      │       │ 模型在框内自由发挥        │
│ 结果不可预测      │       │ 结果部分可预测            │
└──────────────────┘       └──────────────────────────┘

阶段三：Skill               阶段四：Harness
┌──────────────────┐       ┌──────────────────────────┐
│ 人说 WHAT+HOW     │  →   │ 人说 WHAT+HOW+边界         │
│ 结构化为可组合步骤│       │ 模型在边界内被验证执行     │
│ 人在步骤间可干预  │       │ 约束从"正向"到"负向+验证" │
└──────────────────┘       └──────────────────────────┘

阶段五（本方案）：组合式 Harness
┌──────────────────────────────────────────────────────┐
│ 不是一套固定的 Harness，而是按任务类型动态组合的模块   │
│ + 进化引擎持续优化 Harness 本身                       │
│ + 黑板系统提供连续性和可视化                          │
│ 人定义 Harness 的组装规则和进化方向                    │
└──────────────────────────────────────────────────────┘
```

**核心趋势：每一步，人都往后退一步，但系统变得更可靠一步。**

### 3.2 组合式 Harness 模块类型

| 模块类型 | 职责 | 示例 | 装配触发条件 |
|----------|------|------|-------------|
| **安全模块** | 禁止危险操作 | 禁止直接操作 DOM、禁止硬编码密钥 | 所有任务默认加载 |
| **架构模块** | 强制架构规范 | 分层架构检查、依赖方向验证 | 检测到项目有架构定义 |
| **性能模块** | 性能基线检查 | API 超时检查、大文件读取告警 | 涉及 I/O 或网络操作 |
| **风格模块** | 代码风格一致性 | 命名规范、文件组织规则 | 所有任务默认加载 |
| **测试模块** | 测试覆盖检查 | 新代码必须带测试、覆盖率阈值 | 涉及功能变更 |
| **领域模块** | 业务规则约束 | 密码最短长度、金额精度规则 | 按任务领域动态加载 |

### 3.3 装配规则

```
输入：任务描述 → 任务分类器 → 输出：Harness 模块组合

任务分类器：
  · 前端组件开发 → {UI规范, 可访问性, 浏览器兼容, 测试}
  · API 开发      → {接口契约, 安全扫描, 性能基线, 测试}
  · 数据库变更    → {迁移规范, 索引检查, 数据安全, 回滚验证}
  · 重构          → {架构规范, 回归检查, 测试覆盖, 性能对比}

模块冲突检测：
  · 子范畴交的非空性检查——保证有足够路径完成任务
  · 冲突 → 降级策略或人工仲裁
```

## 四、长程编程机制

### 4.1 推理衰减的本质

LLM 的推理不是被人打断的，不是被 Harness 阻断的——**是它自己"觉得做完了"，然后就停了。** 这不是 bug，是机制：

```
初始 prompt P 的影响随着生成长度增加而指数衰减：

t₁  时：P 的注意力权重 ≈ 1.0
t₁₀₀ 时：P 的注意力权重 ≈ 0.3
t₁₀₀₀ 时：P 的注意力权重 ≈ 0.05

模型更多地在"延续自己刚才说的"，而不是"回到原始目标"。
```

**人类编程**：目标一直悬在工作记忆中，每一步都对照检查 → 直到真正达成。

**LLM 编程**：目标在第一步注意力最强 → 逐渐被当前文本淹没 → 当前文本形成"完整感"时就停了 → 不管目标是否真的达成。

### 4.2 三大对抗机制

#### 机制一：目标重注入（任务图追踪器）

不让目标离开注意力窗口。每完成一个子任务 / 每生成 N 个 token，系统自动在上下文中插入目标摘要和任务图：

```
[Harness 注入到 Agent 上下文]

当前任务目标：实现用户登录功能
任务图状态：
  ☑ 数据库用户表 — 已完成
  ▶ 注册接口 — 进行中（第 2 次尝试，上次失败原因：密码哈希未加盐）
  ○ 登录接口 — 待执行
  ○ Token 生成 — 待执行
  ○ 前端表单 — 待执行
整体进度：████████░░ 38%

请继续执行当前子任务。
```

#### 机制二：决策外化（决策分级器 + 决策日志）

不让模型用内部状态记东西。每次 Level 2 以上的决策，写入决策日志，作为后续上下文的固定部分：

```
决策分级标准：

Level 1 — 实现细节 → 自主决定，不记录
  例：变量命名、函数拆分方式

Level 2 — 技术选择 → 自主决定 + 记录原因
  例：选哪个第三方库、缓存策略

Level 3 — 架构决策 → 暂停，列出利弊，等待确认
  例：微服务还是单体、数据库选型

Level 4 — 业务规则 → 必须询问
  例：密码最短几位、超时后跳转哪个页面
```

**决策分级器本身是一个可插拔的 Harness 模块**——创业团队的 L2/L3 边界和银行系统完全不同。

#### 机制三：强制续写（行为监控器）

当模型表现出"结束倾向"时，不信任它，而是检查事实：

```
监控信号：
  · 循环检测：连续 3 次修改同一个文件 → ⚠️ 可能卡住
  · 失败率：测试连续失败 5 次 → 🔴 可能方向错误
  · 时间预算：子任务超预期 2 倍 → ⚠️ 重新评估
  · 过早结束：输出"完成"但任务图还有未完成子任务 → 🔴 强制续写

强制续写注入：
  "你声明任务完成，但以下子任务尚未完成：
   - Token 生成
   - 前端表单
   请继续执行。"
```

### 4.3 执行循环

```
┌─────────────────────────────────────────────────┐
│  由 Harness 驱动，不依赖 Agent 的自我认知          │
│                                                 │
│  1. 从任务图中取下一个子任务                      │
│  2. 构建上下文：                                 │
│     - 目标摘要                                   │
│     - 当前任务图（整体进度）                      │
│     - 决策日志（已做的关键决策）                  │
│     - 当前子任务描述                              │
│  3. Agent 生成代码                               │
│  4. 行为监控器检查：                             │
│     - 过早结束？→ 强制续写，回到步骤 3           │
│     - 卡住？→ 暂停，整理信息，通知人类            │
│     - 正常 → 继续                                │
│  5. 审查官验证产出                               │
│  6. 更新任务图 → 标记完成，更新决策日志           │
│  7. 任务图为空？→ 真正完成                       │
│     否则 → 回到步骤 1                            │
└─────────────────────────────────────────────────┘
```

**关键原则：Harness 不信任 Agent 知道"什么时候该停"。Harness 只看事实——任务图空了才叫完成。**

## 五、黑板系统

### 5.1 三重身份

```
┌─────────────────────────────────────────┐
│              黑  板                      │
│                                         │
│  身份一：当前 Agent 的工作台              │
│    · 对抗推理衰减                        │
│    · 保持目标在注意力窗口内              │
│                                         │
│  身份二：Context Reset 的交接快照         │
│    · 旧 Agent 停，新 Agent 启            │
│    · 黑板不中断，天然就是最新状态         │
│    · 不需要临时"生成交接文件"             │
│                                         │
│  身份三：人-Agent 的共享视图             │
│    · 人随时能看到整体进度                │
│    · 人可以在看到异常时自主介入           │
│    · Agent 变成黑板上的执行者，不是黑盒   │
│                                         │
└─────────────────────────────────────────┘
```

### 5.2 数据结构

```
黑板 {
  区域1: 任务目标（不可变）
    · 原始需求描述
    · 验收标准
    · 变更记录（如有修改，记录原因）

  区域2: 任务图（持续更新）
    · 子任务列表，每项含：
      - id, 描述, 状态(todo/doing/done/blocked)
      - 依赖关系
      - 优先级
      - 完成标准
    · 整体进度百分比

  区域3: 当前子任务上下文（频繁更新）
    · 当前正在执行的子任务
    · 尝试次数
    · 每次尝试的方案和失败原因
    · 当前阻塞点或下一步计划

  区域4: 决策日志（只追加）
    · 时间戳
    · 决策级别 (L1-L4)
    · 决策内容
    · 决策原因
    · 状态

  区域5: 发现与踩坑（只追加）
    · 问题描述
    · 解决方案
    · 状态（活跃/已解决/已过时）
    · 关联的子任务

  区域6: Harness 状态快照
    · 当前加载的约束模块
    · 已触发的干预和拒绝记录
    · 模块装配快照
}
```

### 5.3 运行时机制

```
Agent 每次行动的循环：

1. Harness 从黑板读取当前状态 → 构建 Agent 的上下文注入
2. Agent 执行 → 产出代码/决策
3. Harness 验证产出
4. Harness 更新黑板：
   · 任务图状态变更
   · 新决策追加到区域 4
   · 新问题追加到区域 5
   · Agent 的"当前思考"更新区域 3
5. 如果触发 Context Reset → 黑板已经是完整的交接状态 → 新 Agent 直接从黑板读取
6. 如果任务完成 → 黑板归档 → 提取可复用知识 → 写入笔记系统
```

### 5.4 黑板 vs 笔记

| | 黑板 | 笔记 |
|---|------|------|
| **定位** | 当前任务的实时状态 | 跨任务的知识积累 |
| **内容** | "现在正在发生什么" | "过去学到过什么" |
| **生命周期** | 任务创建 → 任务结束归档后清空 | 持续积累，不过期 |
| **可见性** | Harness + 当前 Agent + 人 | Agent 私有 |
| **维护者** | Harness（自动）+ Agent（当前思考） | Harness（从归档黑板中提取） |
| **交接作用** | 直接用于 Context Reset | 新任务启动时注入历史经验 |
| **读者** | 当前 Agent、下一个 Agent、人 | 未来的 Agent、人 |

## 六、笔记系统

### 6.1 定位

如果说黑板解决的是"这次任务不迷路"，笔记解决的是"下次任务能复用上次的经验"。

### 6.2 内容结构

```
笔记条目 {
  类型: "踩坑" | "发现" | "学到" | "决策" | "待办"
  时间戳: 创建时间
  触发任务: 关联的任务 ID
  标签: [模块名, 技术栈, 问题类型]
  内容: {
    当时的情况: "..."
    做了什么: "..."
    结果如何: "..."
    以后该怎么做: "..."
  }
  状态: 活跃 | 已解决 | 已过时
}
```

### 6.3 检索与注入

```
新任务开始时：
  1. 解析任务涉及的技术栈和模块
  2. 从笔记库中检索相关条目（按相关性和时效性排序）
  3. 将 Top-N 条注入到初始上下文
  4. Agent 开始工作时已经知道：
     - "这个项目 Node 是 18 版本"
     - "错误处理统一用中间件模式"
     - "上次 bcrypt 有兼容问题，改用 argon2"
```

### 6.4 笔记来源

```
任务完成 → 黑板归档 → Harness 分析 →

  区域 4（决策日志）→ 提取关键决策模式 → 写入项目笔记
  区域 5（踩坑记录）→ 提取通用坑 → 写入项目笔记
  区域 1（目标+变更）→ 记录需求演化 → 写入项目笔记
```

## 七、Context Reset 机制

### 7.1 为什么不压缩

```
压缩方案的问题：
  原始： "bcrypt 与 Node 22 不兼容，尝试了 v5.0.0 和 v5.1.0 都不行，
          最终降级到 Node 18 LTS，同时修改了 CI 配置的 Node 版本"
  压缩后： "遇到过 bcrypt 版本问题，已解决"

  丢失的信息：
  - 具体是哪个版本冲突
  - 尝试过哪些方案
  - 最终解决方案是什么
  - 影响了哪些配置文件

  结果：新上下文中 Agent 看似知道发生了什么，实际上失去了关键细节。
        后续决策基于模糊摘要，容易重复犯错。
```

**压缩的本质问题：它试图用"概括"替代"记忆"，但编程中的很多关键信息是不可概括的。**

### 7.2 方案：新 Agent + 黑板交接

```
不是：压缩历史 → Agent 继续（同一个 Agent，模糊记忆）

而是：
  旧 Agent（上下文满了）
    │
    │ 黑板一直在被 Harness 维护，天然是最新状态
    │ 不需要临时"生成交接文件"
    ▼
  新 Agent（干净上下文窗口）
    │
    │ 初始 prompt 中包含完整黑板内容
    │
    ▼
  继续执行（新大脑，但知道之前发生的所有关键事实）

用户视角：会话没有中断，只是"换了一个执行者"
```

### 7.3 触发策略

```
触发条件：

1. 上下文使用率达到阈值（70-80%）
   → 当前子任务完成后触发
   → 不在子任务中间打断

2. 子任务自然完成时
   → 检查上下文使用率
   → 如果超过阈值，就在这个自然断点交接

3. 遇到阻塞需要等待时
   → Agent 被阻塞，等待人工干预
   → 此时交接成本最低，因为本来就要停

原则：不在 Agent 正在"想"的时候打断它，
     在它完成一个可交付的步骤后交接。
```

### 7.4 完整流程

```
1. Harness 检测到触发条件
   （上下文使用率超阈值 且 当前子任务已完成）

2. 黑板已是最新状态（因为它一直被 Harness 维护）
   → 不需要额外"生成交接文件"

3. 旧 Agent 被挂起
   → 其执行记录写入因果账本

4. 新 Agent 启动
   → 干净上下文窗口
   → 初始 prompt 注入黑板完整内容 + 指令：
     "你正在接手一个进行中的任务。
      请先仔细阅读以下状态黑板，理解当前状态，
      然后从任务图的待执行列表中取出下一个子任务继续执行。"

5. 新 Agent 继续执行
   → 更新黑板（与旧 Agent 完全一致的方式）
   → 用户无感知

6. 循环：新 Agent 继续工作，直到再次触发交接条件
```

### 7.5 与传统方案的对比

| | 上下文压缩 | Context Reset（本方案） |
|---|-----------|----------------------|
| 交接内容 | Agent 自我总结的模糊摘要 | Harness 基于事实数据的结构化黑板 |
| 任务状态来源 | 依赖 Agent "记住" | 从任务图追踪器读取，客观 |
| 决策记录 | 可能丢失 | 决策日志独立持久化，不丢失 |
| Harness 状态 | 不传递 | 模块装配快照传递，新 Agent 继承相同约束 |
| 可重演性 | 交接点前后可能断链 | 因果账本全程记录，交接也是账本事件 |
| Agent 身份 | 同一个 Agent（模糊记忆） | 新 Agent（干净上下文 + 完整状态） |

## 九、进化引擎（初步）

### 9.1 定位

进化引擎是 Harness 的自我优化机制。它不是一次性配置，而是持续从 Agent 的执行数据中学习，优化约束规则本身。

### 9.2 进化维度

```
一个好的进化步骤 C_H(t) → C_H(t+1) 满足：
  · 排除了逃逸事件对应的态射（安全性提升）
  · 没有排除必要的任务完成路径（功能保留）
  · 冲突减少（内部一致性提升）
```

### 9.3 数据来源

```
进化引擎的输入：

1. 黑板归档 → 探测模式
   · 哪些子任务经常卡住？→ 可能是任务拆分粒度的信号
   · 哪些决策经常被推翻？→ 可能是决策分级边界不对

2. 审查官日志 → 规则有效性
   · 哪些规则从未触发？→ 可能是冗余规则
   · 哪些规则触发后 Agent 仍然绕过？→ 规则需要加强

3. 笔记系统 → 知识演化
   · "踩坑"条目中哪些问题反复出现？→ 需要新增约束
   · "已过时"条目 → 约束可以放宽或删除

4. 人的干预记录 → 信任边界
   · 人在哪些点主动介入？→ 决策分级可能需要调整
   · 人纠正了什么？→ 可以编码为新的验证规则
```

### 9.4 进化的"好"的标准（三要素）

| 标准 | 含义 | 检测方式 |
|------|------|---------|
| **安全性提升** | 新的逃逸路径被排除 | 审查官拒绝率下降后稳定 |
| **功能保留** | 没有误杀合法的任务路径 | 任务完成率不下降 |
| **内部一致性** | 规则间冲突减少 | 冲突检测通过率提升 |

## 十一、判定逻辑的数学基础

前述架构中有四个关键判定点缺乏可操作的形式化定义：

- **L2/L3 边界**：什么决策自己定，什么决策必须问人？
- **卡住检测**：试了几次失败后该放弃还是继续？
- **任务拆分的粒度**：子任务多大算合理？
- **行为异常阈值**：循环几次算"卡住"？

这些不是拍脑袋的常数，而是有对应数学模型的判定问题。本章给出四个模型的协同架构。

### 11.1 粗糙集：决策分流的第一层

L2 和 L3 之间的那条线没法画成一条精确的线——因为编程决策本身的边界就是模糊的。粗糙集 (Rough Set Theory) 的解法是：**不画线，画三个区域。**

```
粗糙集的三区域划分：

┌──────────────────────────────────────────────┐
│                                              │
│  ┌──────────────────────────────┐            │
│  │  下近似（POS — 确定 L2）     │            │
│  │                              │            │
│  │  变量命名、函数拆分方式      │            │
│  │  代码格式、import 排序       │            │
│  │  注释措辞、日志级别选择      │            │
│  │  文件内的组织结构            │            │
│  └──────────────────────────────┘            │
│                                              │
│  ┌──────────────────────────────┐            │
│  │  边界区域（BND — 不确定）    │            │
│  │                              │            │
│  │  第三方库选型                │            │
│  │  缓存策略选择                │            │
│  │  API 设计风格（REST/GraphQL）│            │
│  │  文件组织/目录结构           │            │
│  │  错误处理策略                │            │
│  │  → 进入贝叶斯逐例判定       │            │
│  └──────────────────────────────┘            │
│                                              │
│  ┌──────────────────────────────┐            │
│  │  负域（NEG — 确定 L3/L4）    │            │
│  │                              │            │
│  │  数据库选型（L3）            │            │
│  │  架构范式选择（L3）           │            │
│  │  密码规则/支付逻辑（L4）     │            │
│  │  用户可见的交互流程（L4）    │            │
│  │  权限/认证方案（L3）          │            │
│  └──────────────────────────────┘            │
│                                              │
└──────────────────────────────────────────────┘
```

**为什么粗糙集而不是概率论？**

粗糙集不需要概率。它只基于"哪些属性已知"来分类。对于 L2/L3 问题，属性包括：

| 属性 | 含义 |
|------|------|
| 影响模块数 | 决策影响多少个文件/模块 |
| 不可逆性 | 决策一旦做出，改回去的成本 |
| 安全性影响 | 决策是否涉及数据安全/权限 |
| 用户可见性 | 决策是否改变用户看到的行为 |
| 先例存在性 | 项目中是否有类似决策可参考 |

粗糙集的判定规则是纯粹的 if-then 逻辑，不依赖统计——这正是 Harness 领域模块可以定义的东西。**安全模块标注"安全性影响=高"的决策点，自动从下近似移除，进入边界区域。**

### 11.2 贝叶斯决策论：边界区域的逐例判定

粗糙集处理不了的边界区域决策，用贝叶斯决策论做精确判定。

**核心公式**

```
Agent 在决策点 D 有两个行动可选：

  a₁: 自主决定（L2）
  a₂: 暂停询问人类（L3）

每个行动的期望代价：

  E[代价(a₁)] = P(错误 | 自主, D) × C(错误影响) + P(正确 | 自主, D) × 0
  E[代价(a₂)] = C(询问)


判定规则：选择 a₂（询问）当且仅当

  P(错误 | 自主, D) × C(错误影响)  >  C(询问)
```

**三个变量的估计**

```
P(错误 | 自主, D) —— 不确定度

  来源：LLM 在决策点 D 上的输出分布熵
  · 如果模型对"用 A 还是 B"的输出概率是 (0.51, 0.49) → 高不确定度
  · 如果输出概率是 (0.95, 0.05) → 低不确定度

  校准：LLM 的原始概率不可信，需要 Harness 层做校准
  · 对于"选库"类决策，即使模型输出 0.9 的置信度，实际准确率可能只有 0.7
  · 校准因子由历史决策的"被推翻率"统计得出

C(错误影响) —— 代价的量化

  C(错误影响) = w₁×M + w₂×I + w₃×S + w₄×U

  其中：
  · M = 影响模块数（归一化）
  · I = 不可逆性等级（1-5）
  · S = 安全性影响等级（1-5）
  · U = 用户可见性等级（1-5）
  · w₁...w₄ = 项目级可配置权重

C(询问) —— 查询代价

  C(询问) = 时间成本 + 上下文切换成本 + 人的不耐烦成本

  不同场景的查询代价不同：
  · 人在线且空闲 → C(询问) = 低
  · 人在忙或离线 → C(询问) = 高
  · 批量询问 > 频繁打断 → 鼓励积累到子任务边界再问
```

**为什么不是纯概率？**

P(错误) 很难精确估计。LLM 的置信度不校准——它可能 95% 置信地说一个错误答案。所以贝叶斯公式只是方向，实际落地需要**可能性理论**来补充。

### 11.3 可能性理论：当概率不可靠时

贝叶斯框架要求精确的 P(错误)，但编程中的不确定性往往是认知性的——"我不知道哪个方案更好"，而不是"我掷了 100 次骰子统计出 A 方案胜率 0.7"。可能性理论 (Possibility Theory) 专门处理这种"不完全信息"场景。

**概率论 vs 可能性理论**

| | 概率论 | 可能性理论 |
|---|--------|-----------|
| 核心问题 | "这件事发生的频率是多少？" | "这件事可能到什么程度？" |
| 合并规则 | P(A∪B) = P(A) + P(B) | Π(A∪B) = max(Π(A), Π(B)) |
| 适合场景 | 有大量同质历史数据 | 单次决策、信息不完整 |
| 对未知的态度 | 均匀分布（强假设） | 最大可能性（保守） |

**可能性理论的落地场景**

可能性理论在系统中有两个核心用途：

```
用途一：替代 P(错误) 的精确值

  不要求 P(错误) = 0.73
  只要求 Π(错误) ∈ {极低, 低, 中, 高, 极高}

  这个可能性等级由 Harness 领域模块定义：
  · 安全模块标记"操作 DOM" → Π(出错造成严重后果) = 极高
  · 架构模块标记"选数据库" → Π(出错造成严重后果) = 高
  · 风格模块标记"命名不一致" → Π(出错造成严重后果) = 低

用途二：生成"为什么问人"的解释

  当 Agent 决定询问时，附带的理由不是模糊的"我不确定"：

  "暂停执行，需要确认：
   当前决策：密码哈希算法选择
   可能性评估：Π(选错导致安全漏洞) = 高
   影响域：所有用户认证流程（3个模块，12个文件）
   替代方案：[bcrypt, argon2, scrypt] 各有 trade-off
   请选择或批准自主评估。"

  这比"我不确定，你帮我看看"的专业度提升了一个量级。
```

**可能性与贝叶斯的协作**

```
贝叶斯判定：用 P(错误) 做精确计算 → 判定 L2 或 L3
可能性判定：当 P(错误) 不可得时，用 Π(错误) 做保守估计 → 宁可多问
可能性解释：无论哪个框架做的判定，可能性等级始终生成，作为给人类的上下文
```

### 11.4 最优停止理论：卡住检测的数学基础

行为监控器里的"卡住检测"——Agent 在子任务上试了几次都失败，"连续 3 次"、"连续 5 次"这些阈值从哪来？

数学上这是**最优停止问题 (Optimal Stopping Problem)** 的一个特例。

**形式化**

```
Agent 在一子任务上已经尝试了 n 次，全部失败。

面临选择：
  · 继续尝试（a_continue）：可能成功，也可能再失败
  · 放弃并切换策略（a_stop）：损失这 n 次的投入，重新评估方向

最优策略：当继续尝试的期望收益低于停止的期望收益时，停止。

形式化：
  V_continue(n) = P(下次成功 | 已失败 n 次) × 成功收益 - 单次尝试成本
  V_stop(n)     = - 已投入成本(n) + 重新评估的期望收益

  当 V_continue(n) < V_stop(n) 时，停止。
```

**阈值不是常数，是动态的**

"连续 3 次"和"连续 5 次"这些数字不能写死。它们由三个因素动态决定：

```
阈值 ∝ 单次尝试成本 / (成功收益 × P(下次成功))

具体：

1. 单次尝试成本低 → 阈值可以更高（多试几次）
   · 改一行代码：成本极低，阈值可以到 8-10
   · 重构整个模块：成本高，阈值应该在 2-3

2. P(下次成功 | 历史失败) 的衰减速度
   · 如果每次失败的类型不同（不同原因），P 衰减慢 → 阈值可以更高
   · 如果每次失败的原因相同（同一个 bug 反复出现），P 衰减快 → 阈值应该更低

3. 外部因素
   · 人在线且有空 → 停止后可以立即获得人的指导 → 阈值可以更低
   · 人不在线 → 停止也无法推进 → 阈值可以更高（再试几次）
```

**序贯概率比检验 (SPRT) 的实现**

```
SPRT 的简化版本：

记录每次尝试的结果：成功(1) / 失败(0)
  序列：[0, 0, 0, 0, 0]  ← 连续 5 次失败

两个假设：
  H₀: 成功率 ≥ 0.3（方向正确，只是运气不好）
  H₁: 成功率 < 0.1（方向错误）

似然比：
  LR = P(序列 | H₁) / P(序列 | H₀)
     = 0.9⁵ / 0.7⁵ ≈ 2.3

如果 LR > 阈值_A（比如 5）→ 接受 H₁，认定方向错误，停止
如果 LR < 阈值_B（比如 0.2）→ 接受 H₀，认定方向正确，继续

2.3 在两个阈值之间 → 继续采样（再试一次）

当前序列 [0,0,0,0,0]：LR = 2.3，不够 5 → 再试一次
如果再失败 [0,0,0,0,0,0]：LR = 0.9⁶/0.7⁶ ≈ 3.0 → 还不够 → 再试
如果再失败 [0,0,0,0,0,0,0]：LR = 0.9⁷/0.7⁷ ≈ 3.9 → 接近了
如果再失败 [0,0,0,0,0,0,0,0]：LR = 0.9⁸/0.7⁸ ≈ 5.1 → 超过阈值 5，触发卡住警报
```

**这意味着"连续 8 次失败"是数学推导出来的，不是拍脑袋的 3 或 5。** 而且阈值_A 和阈值_B 是项目级可配置的——高安全要求的项目把阈值_A 调低（更早放弃，更快报警），快速迭代的项目把阈值_A 调高（更愿意让 Agent 多试）。

## 十二、系统各环节的数学基础

### 12.1 推理衰减：指数衰减模型

第四章定性描述了"注意力权重随 token 数衰减"，本节给出精确形式。

**注意力权重的衰减函数**

```
令 A(t) 为原始目标在第 t 个 token 生成时的注意力权重。

基本模型（指数衰减）：

  A(t) = A₀ · e^(-λt)

  其中：
  · A₀ = 1.0（初始注意力权重）
  · λ = 衰减率，由模型架构和 prompt 结构决定
  · t = 已生成的 token 数（或等价的上下文消耗比例）

典型值估计：
  · λ ≈ 0.002-0.005 对于大多数 LLM
  · 当 t = 200 时，A(200) ≈ 0.67-0.37
  · 当 t = 500 时，A(500) ≈ 0.37-0.08
  · 当 t = 1000 时，A(1000) ≈ 0.14-0.007

衰减的含义：
  A(t) 并非"模型忘记目标"，而是目标在注意力分布中被当前文本淹没。
  当 A(t) < 某个临界值 A_crit 时，模型行为从"目标驱动"转为"文本自驱动"。
```

**比指数更精确的模型**

实际注意力衰减不是理想指数，因为中间有目标相关 token 会"唤起"注意力。更精确的模型是**带唤起的衰减**：

```
A(t) = A₀ · e^(-λt) + ∑ᵢ wᵢ · e^(-λ(t - tᵢ)) · I(t > tᵢ)

其中：
  · tᵢ 是第 i 次"唤起"事件的发生时间（如提到目标关键词）
  · wᵢ 是唤起强度
  · I(t > tᵢ) 是指示函数（唤起后才生效）

每次目标重注入就是一个人工制造的唤起事件，wᵢ 由注入内容的完整度和位置决定。
```

**临界衰减阈值的推导**

```
A_crit 的估计：

  当 A(t) 衰减到与背景噪声注意力可比时，目标不再可区分。

  背景噪声 ≈ 1/N，其中 N = 上下文中可注意的 token 数。
  对于 200K 上下文，背景噪声 ≈ 5×10⁻⁶。

  实际 A_crit 远高于此，因为需要的是"主导性注意"而非"可区分的注意"。
  经验估计：A_crit ≈ 0.05-0.15（即目标占注意力 5-15% 以上才有效驱动行为）。

t_crit = -ln(A_crit/A₀) / λ

  当 λ=0.003, A_crit=0.10: t_crit ≈ 767 tokens
  当 λ=0.003, A_crit=0.05: t_crit ≈ 999 tokens
```

**这给出了目标重注入频率的硬上限：必须在 t_crit 之前重注入。** 如果 λ=0.003，每 500-700 token 至少需要一次重注入。

### 12.2 目标重注入：信息刷新率

知道"必须重注入"后，下一个问题是"最优频率是多少"。注入本身有代价——消耗 token、打断 Agent 的思维流。

**形式化为刷新决策问题**

```
每 T 个 token 有一次注入机会。

状态：A(t)，目标的当前注意力权重
行动：注入（付出代价 C_inj，将 A 重置为 A₀）或跳过（A 继续衰减）
目标：在总 token 预算 B 内，最大化"有效注意力积分"

有效注意力积分：
  ∫₀ᴮ A(t) · I(A(t) ≥ A_crit) dt

优化问题：
  选择注入间隔 T₁, T₂, ... 使得有效注意力积分最大，
  且 ∑ 注入次数 × C_inj ≤ 总注入预算。
```

**等间隔注入的解析解**

```
假设等间隔注入（每 T 个 token 注入一次），注入代价 = c 个 token。

有效注意力积分（单周期）：
  S(T) = ∫₀ᵀ e^(-λt) dt = (1 - e^(-λT)) / λ

带代价的有效积分（单周期）：
  S_eff(T) = S(T) / (T + c)

最优 T* 使得 S_eff(T) 最大化：
  d/dT [ (1-e^(-λT)) / (λ(T+c)) ] = 0

简化：T* ≈ √(2c/λ) （当 λT 较小时）

示例：
  c = 200 tokens（注入开销），λ = 0.003
  T* ≈ √(2 × 200 / 0.003) ≈ √133333 ≈ 365 tokens

这意味着：
  · 每 365 个 token 注入一次目标摘要
  · 每次注入花费 200 token
  · 注入间距不足以等到自然衰减到 A_crit 以下
  · 这是一个保守策略——宁可多注入，不让目标丢失
```

**自适应注入策略**

等间隔不是最优的。自适应策略更高效：

```
自适应策略：
  1. 监测 A(t) 的估计值（基于自上次注入后的 token 数）
  2. 当 A(t) 接近 A_crit 时触发注入，而非固定间隔
  3. 如果 Agent 当前输出中出现目标关键词 → A(t) 被自然唤起 → 推迟注入
  4. 如果 Agent 即将完成一个子任务 → 在该子任务完成后立即注入

实际节省：
  自适应策略相比等间隔，可以减少 20-30% 的注入次数，
  同时保持相同水平的注意力维持。
```

### 12.3 黑板 Token 预算分配：约束优化

黑板六个区域全部注入上下文不现实。需要决定：哪些区域始终注入、哪些只注入摘要、哪些按需注入。

**形式化：预算约束下的信息价值最大化**

```
给定：
  · 总 token 预算 B_blackboard（如 2000 tokens）
  · 六个区域，每个区域 i 有：
    - 原始内容长度 L_i
    - 信息价值函数 V_i(x)，表示分配 x 个 token 给该区域能传递多少有效信息
    - 最低表示长度 L_min_i（摘要到多短就不可用）

目标：
  选择每个区域的分配 x_i，使得 ∑ V_i(x_i) 最大化
  满足：∑ x_i ≤ B_blackboard, x_i ≥ L_min_i 或 x_i = 0
```

**各区域的信息价值函数**

```
区域1（任务目标）：V₁(x) = min(1, x/L₁)
  → 线性：每个 token 都等值，但超过完整内容后无增益
  → 策略：始终注入完整内容（通常 < 200 token）

区域2（任务图）：V₂(x) = 1 - e^(-αx)
  → 前几个子任务信息密度最高（进度、当前节点），后续递减
  → 策略：注入全部待执行/进行中/阻塞节点 + 最近完成的 2 个节点

区域3（当前上下文）：V₃(x)
  → 高时效性，但高冗余（Agent 已经在上下文中见过）
  → 策略：只注入摘要（当前子任务名 + 尝试次数 + 上次失败原因，< 100 token）

区域4（决策日志）：V₄(x) = 1 - e^(-βx)
  → 早期决策信息价值高，旧的决策可压缩
  → 策略：最近 3 条完整注入，其余按时间衰减压缩为一行摘要

区域5（发现与踩坑）：V₅(x) = f(活跃条目数)
  → 活跃问题高价值，已解决问题可压缩
  → 策略：活跃条目完整注入，已解决条目只注入标题

区域6（Harness 状态）：V₆(x) = 常数（小且稳定）
  → 模块列表 + 最近干预，通常 < 100 token
  → 策略：始终完整注入
```

**闭式分配方案**

```
B_blackboard = 2000 tokens 的默认分配：

区域1（目标）：      200 tokens  → 完整
区域2（任务图）：    600 tokens  → 优先级剪裁
区域3（当前上下文）： 100 tokens  → 摘要
区域4（决策日志）：  400 tokens  → 最近3条完整 + 其余一行一条
区域5（发现问题）：  500 tokens  → 活跃完整 + 已解决标题
区域6（Harness）：   100 tokens  → 完整
预留/弹性：          100 tokens

自适应调整：
  · Context Reset 交接时：区域3 扩充到 400（需要给新 Agent 更多上下文）
  · 任务中期：区域2 可缩减到 400，把预算给区域5
  · 任务尾声：区域2 缩减，区域4 可归档到笔记
```

### 12.4 笔记检索：相关性排序与时效衰减

第六章描述了笔记系统，但检索机制需要数学模型——新任务开始时如何从历史笔记中选 Top-N。

**相关性评分：多因子排序**

```
笔记 j 对当前任务的相关性评分：

  Score(j) = Rel(j) × Fresh(j) × Freq(j)

其中每个因子归一化到 [0,1]。
```

**因子一：内容相关性 Rel(j)**

```
Rel(j) = 基于标签+内容的匹配度

标签匹配（Jaccard 相似度）：
  Sim_tags = |标签(j) ∩ 标签(任务)| / |标签(j) ∪ 标签(任务)|

内容匹配（嵌入余弦相似度）：
  Sim_content = cos(embed(笔记摘要), embed(任务描述))

融合：
  Rel(j) = α · Sim_tags + (1-α) · Sim_content, α = 0.6
  → 标签权重更高，因为标签是结构化的、人审核过的
```

**因子二：时效衰减 Fresh(j)**

```
Fresh(j) = e^(-γ · Δt)

其中：
  · Δt = 当前时间 - 笔记创建时间（天）
  · γ = 衰减率

默认 γ = ln(2)/90 ≈ 0.0077（半衰期 90 天）

特殊情况：
  · "踩坑"类型笔记：γ 更小（半衰期 180 天）→ 技术坑可能持续有效
  · "学到"类型笔记：γ 更大（半衰期 60 天）→ 主动学到的经验可被新技能取代
  · 笔记被标记"已过时"：Fresh(j) = 0 → 不参与检索
```

**因子三：复用频率 Freq(j)**

```
Freq(j) = min(1, use_count(j) / use_threshold)

其中：
  · use_count(j) = 该笔记被检索并注入的次数
  · use_threshold = 达到满分所需的复用次数（如 5 次）

含义：被反复引用的笔记更可能是"真的有用"的通用知识。
```

**Top-N 选择**

```
检索流程：
  1. 计算所有活跃笔记的 Score(j)
  2. 按 Score(j) 降序排列
  3. 选择 Top-N，N 由初始注入预算决定

N 的确定：
  初始注入预算 ≈ 500 tokens（新任务初始上下文中的笔记空间）
  每条笔记平均 ~100 tokens → N = 5

  N 应该自适应：
  · 如果 Score 分布有明显断崖（前三条远高于后续）→ N = 3
  · 如果 Score 分布平滑 → N = min(8, 预算/平均笔记长度)
```

### 12.5 Context Reset 最优触发：动态规划

第七章提到触发阈值为"70-80% 上下文使用率"，这个数字需要数学推导。

**形式化为最优停止问题**

```
状态：
  · u = 当前上下文使用率（0-1）
  · k = 当前子任务是否完成（0/1）
  · n = 任务图中剩余子任务数

行动：
  · 继续：Agent 执行下一个子任务，u 增长 Δu
  · 重置：触发 Context Reset，付出切换代价 C_switch

C_switch 的组成：
  · 交接时间（旧 Agent 停 + 新 Agent 启动）：~固定成本
  · 信息损失风险（黑板不完美的传输）：~正比于当前复杂度
  · 用户感知成本（切换瞬间的短暂停顿）：~常数
```

**简化模型：固定子任务消耗**

```
假设每个子任务消耗相同的上下文增量 Δu：

最优策略是一个阈值 u*：
  · 如果 u ≤ u* 且当前子任务已完成 → 触发重置
  · 如果 u > u* 或当前子任务进行中 → 继续

u* 的推导：

  设：
    · 总 token 预算 = C_max
    · 每个子任务消耗 = Δ_c
    · 切换代价 = C_switch
    · 总子任务数 = N

  最坏情况：在上下文满时被迫切换，代价最高。
  最优情况：在自然断点提前切换，代价最低。

  u* = 1 - (C_switch + Δ_c) / C_max

  典型值：
    C_max = 200K tokens
    C_switch ≈ 3K tokens（交接开销）
    Δ_c ≈ 15K tokens（平均子任务消耗）

    u* = 1 - (3K + 15K) / 200K = 1 - 0.09 = 0.91

  但这是不考虑安全边际的值。加上安全边际（20%）：
    u*_safe = 0.91 × 0.8 ≈ 0.73 → 即 70-75%
```

**这就是 70-80% 阈值的数学来源。** 它由三个参数决定：交接代价、子任务平均消耗、安全边际。不同项目有不同的 Δ_c（前端任务消耗少，数据库迁移消耗多），所以 u* 应该是项目级可配置的，而非全局常数。

**带子任务大小的自适应策略**

```
如果子任务大小差异很大（更实际的情况）：

策略：不在 u 超过阈值时切换，而在"下一个子任务如果执行完了，
      u 会超过安全上限"时切换。

  即：if (u + E[下一个子任务的 Δ_c]) > u_max_safe:
        当前子任务完成后触发重置

  u_max_safe = 1 - C_switch/C_max
```

### 12.6 任务拆分的粒度模型

第四章假设任务图已经存在，但没有讨论任务图本身怎么生成才算合理。子任务拆分太粗（3 步拆完）→ Agent 迷失（每步太大）。拆太细（30 步）→ 开销过大（每步都要注入上下文）。

**粒度的量化：信息熵视角**

```
一个子任务的"大小"可以用执行它需要处理的代码信息量来度量：

  H(子任务) = -∑ p(x) log₂ p(x)

  其中 p(x) 是需要考虑的代码实体的分布。

  例如：
  · "创建用户表" → 涉及 1-2 个文件，决策空间小 → H ≈ 2-4 bits
  · "实现认证流程" → 涉及 5-10 个文件，多个决策点 → H ≈ 10-20 bits
```

**最优粒度的约束条件**

```
子任务不能太小：
  · 上下文注入开销（~200 tokens/步）
  · 如果 H < 某个下限 → 注入开销超过任务本身的信息量 → 浪费

子任务不能太大：
  · 注意力衰减限制：Agent 在执行一个子任务时，子任务内的子目标也会衰减
  · 如果 H > 某个上限 → Agent 在子任务内会迷失

因此：
  H_min ≤ H(子任务) ≤ H_max

  H_min ≈ 注入开销的等效信息量（~5-10 bits）
  H_max ≈ Agent 在单次推理中可保持的信息量（~30-50 bits）

实际对应：
  · H_min 对应：修改一个函数、添加一个字段
  · H_max 对应：创建完整的 CRUD 模块、实现含 3-5 个接口的 API
```

**拆分算法：信息熵阈值分割**

```
自顶向下拆分：

1. 从总目标 G 开始，估计 H(G)
2. 如果 H(G) ≤ H_max → 不拆分，G 就是一个子任务
3. 如果 H(G) > H_max → 将 G 分解为 {G₁, G₂, ..., Gₖ}
   - 分解策略：沿信息依赖边界切分
   - 每个 Gᵢ 的信息熵 H(Gᵢ) ≈ H(G)/k（粗略估计）
4. 递归对每个 Gᵢ 做同样操作
5. 停止条件：所有叶子节点 H ≤ H_max

如果 H_min 无法满足（某些子任务即使不拆分也小于 H_min）：
  → 合并相邻的小子任务，直到 H ≥ H_min
  → 但合并后的 H 不超 H_max
```

**质量的验证指标**

```
一个好的任务拆分的定量指标：

1. 模块性（Modularity）：
    同一子任务内的代码实体耦合度 >
    不同子任务间的代码实体耦合度

2. 平衡性（Balance）：
    H_max / H_min ≤ 5（避免某些子任务远大于其他）

3. 依赖深度（Dependency Depth）：
    任务图的 DAG 深度 ≤ 5（避免过深的依赖链增加阻塞风险）
```

### 12.7 进化引擎的统计检验：规则变更的自动/审批边界

第九章描述了进化引擎，但没有定义什么规则变更自动生效、什么需要审批。这需要统计显著性检验。

**规则有效性的假设检验**

```
给定一条规则 r 及其 N 次触发的历史数据：

H₀（原假设）：规则 r 无效（触发 = 随机的，与真实问题无关）
H₁（备择假设）：规则 r 有效（触发 = 指示真实问题）

观测数据：
  · 触发次数：n_trigger
  · 其中"真正阻止了问题"：n_true_positive
  · 其中"误杀"（阻止了正确代码）：n_false_positive

检验统计量：
  精确率 = n_true_positive / n_trigger
```

**自动审批的统计条件**

```
规则变更类型 A：自动生效（无需人工审批）
  条件：
    1. 精确率的 95% 置信下限 > 0.7
       → CI_lower = 精确率 - 1.96 × √(精确率×(1-精确率)/n_trigger)
       → 如果 CI_lower > 0.7，则有 95% 置信度认为规则精确率 ≥ 70%
    2. n_trigger ≥ 20（足够样本量）
    3. n_false_positive = 0（没有被推翻过）
    4. 变更类型为"参数微调"（如阈值从 3 调到 4），而非"新增禁止项"

规则变更类型 B：建议 + 审批
  条件：
    1. 精确率的 95% 置信下限 > 0.5（中等置信度）
    2. n_trigger ≥ 10
    3. 或：变更类型为"新增禁止项"

规则变更类型 C：仅报告（不自动建议）
  条件：
    1. n_trigger < 10（样本不足）
    2. 或：精确率过低（< 0.3）
```

**误杀率的控制：FDR（错误发现率）**

```
进化引擎在建议"删除冗余规则"时，需要控制误删风险。

FDR = E[被删的有效规则数 / 总删除数]

Benjamini-Hochberg 过程：
  1. 对每个候选删除规则计算 p-value（基于其无效性假设）
  2. 按 p-value 升序排列
  3. 找到最大的 k 使得 p(k) ≤ k/m × α
     （m = 候选删除总数，α = 目标 FDR 水平，如 0.1）
  4. 删除前 k 条规则

这保证：在建议删除的一批规则中，误删率控制在 α 以内。
```

**多臂老虎机视角**

```
进化引擎在探索"应该用哪个阈值"时，本质上是多臂老虎机问题：

  · 每个候选阈值 = 一个臂
  · 选择某个阈值并观察结果 = 拉一次臂
  · 奖励 = 该阈值下规则的表现（精确率 + 召回率）

ε-greedy 策略：
  · 以概率 ε 随机尝试新阈值（探索）
  · 以概率 1-ε 使用当前最佳阈值（利用）

  ε 随规则稳定度递减：
    ε = ε₀ / (1 + k × 规则稳定使用天数)
    ε₀ = 0.2
    k = 衰减系数

汤普森采样（更优）：
  · 每个候选阈值维护一个 Beta 分布（成功次数, 失败次数）
  · 每次决策时从各分布中采样，选择采样值最高的阈值
  · 自然平衡探索与利用
```

### 12.8 Harness 模块装配：多目标优化

第三章定义了模块装配规则（前端任务→{UI规范, 可访问性, 浏览器兼容}），但模块选择可以形式化为更精确的多目标优化问题。

**形式化**

```
任务 t 触发的 Harness 装配问题：

输入：
  · 任务特征向量：f = [领域, 技术栈, 变更类型, 影响范围, 优先级]
  · 候选模块集：M = {m₁, m₂, ..., mₙ}
  · 每个模块 mⱼ 有：
    - 适用性评分：sⱼ(f) ∈ [0,1]  （该模块对任务 t 的适用度）
    - 激活成本：cⱼ           （加载该模块的 token 开销）
    - 冲突矩阵：Cⱼₖ ∈ [0,1]   （模块 j 与模块 k 的冲突度）

决策变量：
  · xⱼ ∈ {0,1}：是否激活模块 j

优化目标：
  最大化：∑ xⱼ · sⱼ(f)           （总适用性）
  最小化：∑ xⱼ · cⱼ              （总成本）
  最小化：∑ⱼ∑ₖ xⱼxₖ · Cⱼₖ        （总冲突）
```

**简化为可操作的装配策略**

```
实际落地不需要在线求解多目标优化。简化策略：

第一层（安全硬约束）：安全模块 → 始终激活，x_safety = 1
第二层（架构匹配）：架构模块 → if 项目有架构定义 → x_arch = 1
第三层（领域匹配）：领域模块 → if sⱼ(f) > 0.5 → xⱼ = 1
第四层（冲突解决）：if Cⱼₖ > 0.3 且两个模块都在候选集中 → 优先保留 sⱼ 更高的

总激活模块数受黑板 token 预算限制：
  ∑ xⱼ · cⱼ ≤ B_harness_section
  B_harness_section ≈ 200 tokens（黑板的 Harness 区域预留）
```

**模块适用性评分 sⱼ(f) 的估计**

```
sⱼ(f) 由以下因素加权得到：

sⱼ(f) = w₁ · δ(领域匹配) + w₂ · δ(技术栈匹配) + w₃ · δ(变更类型匹配)

其中 δ 是指示函数或模糊匹配度。

模块自举：
  · 初始：sⱼ(f) 由人工定义（简单规则表）
  · 进化：从历史数据中学习——如果模块 j 在类似任务中被激活后触发了有效干预，
          则对该类任务的 sⱼ 上调；如果模块 j 被激活但从未触发，
          则对该类任务的 sⱼ 下调。
```

## 附录：关键设计原则

1. **不信任 Agent 的自我认知**——任务完成与否由任务图决定，不由 Agent 声明决定
2. **黑板是唯一真相源**——UI、交接、上下文注入，都从黑板读取
3. **约束从正向到负向+验证**——不是穷举"应该做什么"，而是定义"不能越界"然后自动验证
4. **在自然断点交接**——不在 Agent 思考中途打断
5. **外化一切可外化的状态**——决策日志、踩坑记录、任务图，全部结构化持久化
6. **可视化是信任基础设施，不是锦上添花**——Harness 保证可靠，可视化让人敢信任
